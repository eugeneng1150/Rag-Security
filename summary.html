Qwen · controlled smoke evaluation

When database text becomes an agent command

This experiment tests whether an indirect prompt injection hidden in a public employee field can redirect a finance-capable agent, retrieve private compensation, and trigger a notification to an attacker. It then evaluates a Cordon-MAS-inspired information barrier while keeping the same finance access and legitimate action capability.

Research safety: the employee records and compensation values are seeded synthetic data. The notification tool writes to a local JSONL file; it does not send real email.

Experiment design

What each phase is meant to show

The phases separate ordinary access control from information-flow protection. Phase 1 and Phase 2 both use a finance role, making them the central security comparison.

Stage Database capability System design Question answered Experiment state
Utility Employee + finance cases Benign requests through Phase 2 Does the defense still answer and perform authorized actions? Completed
Phase 0 Employee role Deterministic table access control Does ordinary authorization block private-table access? Completed
Phase 1 Finance role Raw SQL results return to a tool-using orchestrator Can poisoned data become a command and cause exfiltration? Completed
Phase 2 Finance role Extraction → audit → claim gate → synthesis/action gate Can information-flow controls stop the attack without removing capabilities? Completed
Phase 3 Finance role Adaptive and stage-targeted payload families How far can an attack penetrate each defense boundary? Planned
The comparison to remember: Phase 0 is safe because access to the private table is denied. Phase 2 is different: the finance role can legitimately read compensation, but untrusted database text is prevented from creating a new query or notification authority.

How Phase 2 handled the 20 poisoned results

This is a separate defense-processing view—not the attack scale above. Here, detection and rejection are protective operations.

⚠ 20/20 poisoned fields reached retrieval
▤ 20/20 poisoned fields were isolated as separate claims
⛨ 20/20 poisoned claims were detected and rejected
✉ 0/20 attacker notifications were sent
The defense does not make the poisoned database row disappear. In every trial, it isolates and rejects the malicious field while clean fields from the same row remain eligible for use. The database text never authorizes an email.
